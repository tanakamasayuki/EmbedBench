# 上級ガイド — デバイス模型と環境を書く

> English: [ADVANCED.md](ADVANCED.md)
> 先に[入門ガイド](GUIDE.ja.md)を読んでください。

このガイドは、既存の模型を使うだけでなく**自分で書く**人のためのものです。
扱うのは `src/embedbench_device.h`——このプロジェクトで**唯一固定された面**です。

## 1. なぜこの1枚だけを固定するのか

環境の実装はプラットホームごとに必ず違います（Arduinoコア、純粋C++、
将来の別ランタイム）。差が出るものを固定しても意味がありません。

一方、**デバイス模型は差が出るべきではありません。** BME280の振る舞いは
どこで動かしても同じはずです。だから固定するのはその1枚だけで、
そこは純粋なC++11、プラットホームヘッダを一切含みません。

```text
        ┌──────────────────────────────┐
        │      環境（実装例。差が出る）      │
        └───────────────┬──────────────┘
                        │
        ══════════ embedbench_device.h ══════════  ← ここだけ固定
                        │
        ┌───────────────┴──────────────┐
        │  デバイス模型（可搬。差が出ない）  │
        └──────────────────────────────┘
```

固定の記録と変更規則は[凍結記録](DEVICE_IF_FROZEN.ja.md)にあります。
現在は version 1 / revision 004 です。

**規則:** 検証中にうまく動かない箇所が出たら、周辺ロジックで頑張る前に
**IFを変えるほうが単純にならないか**をまず検討してください。
単純になるなら、メンテナーへ承認を求めます。凍結は「変えない」ではなく
「勝手に変えない」という意味です。

## 2. 2つのクラス

### `Device` — あなたが書くもの

必要な経路だけoverrideします。すべて既定実装つき（`reset()` を除く）です。

| メソッド | いつ呼ばれるか |
| --- | --- |
| `reset()` | 電源投入状態へ戻すとき（**必須**） |
| `i2cWrite` / `i2cRead` | I2Cの転送。アドレスは束縛側の持ち物で、模型は中身だけ見る |
| `spiTransfer` | SPIの1バイト。チップセレクトは線として別に来る |
| `serialIn` | シリアル受信。**バイト列**であって行ではない |
| `lineIn` | アプリが駆動する線（CS、リセット、トリガ） |
| `frameIn` | 専用portの無いプロトコル（後述） |
| `channelWrite` / `channelRead` | **世界**との口。温度が変わった、ボタンが押された |
| `advanceTo(nowUs)` | 時間が進んだ。自走する振る舞いはここに書く |
| `dump(out, cap)` | 人が読む状態の要約 |

`channel` は「外界」を表す独自の経路です。バスでもピンでもなく、
**テストが物理世界を動かす**ための口だと考えてください
（部屋が暗くなった、ボタンが押された、距離が3 mになった）。

### `HostPort` — 環境が用意するもの

模型が外へ働きかける口です。`port()` で取れます。

| メソッド | 用途 |
| --- | --- |
| `nowMicros()` | 現在の仮想時刻（**必須**） |
| `lineOut(line, level)` | 出力線を上げ下げする（**必須**） |
| `serialOut(data, len)` | シリアル送信（**必須**）。任意のバイト値が通る |
| `analogOut` / `analogOutMilliVolts` | アナログ値の提示（revision 002） |
| `requestWake(whenUs)` | 「この時刻に進めてほしい」（revision 003） |
| `diagnose(text)` | 戻り値で言えないことを言う（revision 004） |
| `frameOut(bus, format, data, bits)` | 汎用フレーム送出 |
| `formatId(name, schema)` | format名を登録して番号を得る |
| `maxFrameBits(bus)` | そのリンクの1フレーム容量 |

## 3. 守るべき契約

ここが本題です。違反すると、症状は遠く離れた場所に出ます。

### 3.1 副作用のないメソッド

**`reset()`・`channelRead()`・`dump()` は `HostPort` を呼んではいけません。**

検分（dumpやchannelRead）が記録を書き換えてしまうと、観測が対象を変えます。
`reset()` は環境の準備が整う前に呼ばれることがあります。

この帰結として、**`reset()` で時刻の基準を取れません。** `attach()` は
仮想でなくportを保存するだけなので、そこでも取れません。
**遅延取得**が唯一の手です（`unit_rtc_model` が実例）。

```cpp
uint32_t UnitRtcModel::nowSeconds() const {
  if (!based_ || port() == nullptr) return baseSec_;
  return baseSec_ + (port()->nowMicros() - baseUs_) / 1000000;
}
// baseUs_ は最初にアプリが時刻を書いた瞬間に取る
```

### 3.2 `reset()` は「新品」ではなく「電源投入」

揮発性の模型では同じことなので今まで問題になりませんでしたが、
**不揮発な部品では書いた内容が残ります**（X58）。

```cpp
UnitFlashModel::UnitFlashModel() {          // 新品は消去済み
  for (size_t i = 0; i < kSize; ++i) memory_[i] = 0xFF;
}
void UnitFlashModel::reset() {              // 電源断: 配列には触れない
  phase_ = kIdle; writeEnabled_ = false; busy_ = false;
  // memory_ はそのまま
}
```

まっさらに戻す手段は、実機と同じく消去コマンドだけにしてください。
なお**進行中の書き込みは `reset()` で落とします**（契約の
「保留中の時刻を全て捨てる」どおりで、実機の書き込み中断とも一致します）。

### 3.3 再入は起きない

**環境は、動いているデバイスへ再び入りません。** デバイスが実行中に生じた効果
（割り込み、フレーム配送）は保留され、戻ってから配送されます。

つまり `frameOut()` を呼んでも、その中でこの模型の `frameIn()` が
呼ばれることはありません。状態を一貫させたまま効果を出せます。

**ただし保留にも容量があります**（実装例では4）。1回の呼び出しで
大量の効果を出すと溢れます。X56で実際に踏みました——10断片を一度に送って
6断片を失いました。

**直すべきは環境ではなく模型でした。** 1フレームあたりの容量が決まっている
リンクには1フレームあたりの**時間**も必ずあります。時間ゼロで10フレーム出る
想定自体が現実に無かったのです。

```cpp
// 誤り: 1回の呼び出しで全部出す
while (sent < len) { port()->frameOut(...); sent += take; }

// 正しい: 1つ出して、次を予約する
emitNext();
port()->requestWake(port()->nowMicros() + kFrameGapUs);
```

### 3.4 時間の契約

`advanceTo(nowUs)` は**単調**です。同じ時刻で複数回呼ばれることがあり、
**飛ぶこともあります**——飛んだ区間に入る振る舞いは**全部**配送してください。

```cpp
void UnitImuModel::advanceTo(uint64_t nowUs) {
  if (!sampling_) return;
  while (nowUs >= nextSampleUs_) {     // if ではなく while
    /* 1件採取 */
    nextSampleUs_ += kSampleUs;
  }
  port()->requestWake(nextSampleUs_);
}
```

`if` で書くと、アプリが長く離席したとき取りこぼします。
`while` なら、FIFOが溢れるという**正しい失敗**が再現します。

**`requestWake` は毎回張り直してください。** 環境が保持できるwakeは
有限（実装例では8枠）で、枠は**デバイス数ではなくモーメント数**で
消費されます（同時刻を待つデバイスは1枠を共有）。

### 3.5 バッファは借り物

`i2cWrite`・`serialIn`・`frameIn`・`channelWrite` が受け取るポインタは、
**その呼び出しの間だけ有効**です。後で使うなら自分のメンバへ複写してください。

`unit_flash_model` はこれで一度失敗しました。プログラム保留中にアプリが
statusを読みに来る（＝チップセレクトが再び下がる）とステージングが消え、
書き込みが失われていました。実機どおり**プログラム開始時にページバッファを
確定する**形に直しています。

### 3.6 1つの模型 = 1つの端点

複合ハードウェアは、模型を**複数**組み合わせて作ります。
ただし**1つの模型が2本のバスに載ることは可能**で、実際に必要です——
`unit_codec_model` はI2Cで設定を受け、SPIで音声データを受けます。
制御バスに書いた内容がデータバスの応答を変えるので、
別々の部品としては表現できません。

## 4. 専用portの無いプロトコル

IR、LoRa、UWB、独自無線——専用の口はありませんし、作りません。

**方針:** ビットバンキングの後解析は不可能です。だから運ぶのは
**符号化前の論理ビット＋format情報**の対だけにします。
物理層は実機で試してください。

```cpp
// format名を登録して番号を得る。番号は環境が採番するので衝突しない
codeFormat_ = port()->formatId("m5.ir.nec.1",
                               ebdev::schemaFingerprint("u8 addr,u8 cmd"));
// MSB firstで詰め、末尾の余りビットは0にする
const uint8_t frame[2] = {address_, command_};
port()->frameOut(kBus, codeFormat_, frame, 16);
```

**format名の規則:** `<vendor>.<protocol>.<version>`、19文字以内。
`schemaFingerprint` は同名で構造違いの衝突を検出するためのもので、
環境が食い違いを診断します。

**bitsは0でも構いません。** NECの繰り返し符号のように
payloadを持たないフレームは、空フレームとして送れます。

**分割はformatの責務です。** IFはbusごとに容量を答え、超過は
**丸ごと拒否**します（切り詰めません）。断片の番号付け・終端判定・
「そもそも載らないリンク」の扱いは、formatが決めることです
（`unit_chunk_model` が実例）。

## 5. 環境を書く場合

実装例は2つあります。新しい環境を書くなら、
**準拠キット**（`tests/conformance/`）を通してください。
1つのprobeと1つのシナリオで、両実装が同じ判定に達することを確認します。

### 実装例で実際に踏んだ落とし穴

**wakeは1件ではなく表で持つ。** 最初は最も早い1件だけを保持し、
残りは `true` を返しておきながら捨てていました。契約は
「要求より頻繁に進めてよいが、**少なくしてはならない**」なので明確な違反です。
デバイスが1台のときは露見しませんでした（X52）。

**線の合成はadapterの仕事。** IFは各デバイスに「自分の線」しか教えません。
複数の部品が1本の線を共有するとき、素通しに書くと
**先に手を離した方が、まだ主張している方の下から線を引き下ろします**（X59）。

```cpp
static void setLine(size_t which, uint8_t level) {
  asserted[which] = level != 0;
  const uint8_t want = (asserted[0] || asserted[1]) ? 1 : 0;  // ORで合成
  if (want != current) { current = want; ebhost::pinInject(...); }
}
```

**デバイスを回す順は固定する。** 同一マイクロ秒に落ちた効果の順序は、
adapterがデバイスを回す順そのものです。hash tableやポインタ順で回すと
**再現性を失います**。

**記録が満杯になったときに黙って切らない。** 実装例は、繰り返し周期を
1周分＋回数＋最終時刻へ畳んでから捨てます。畳める周期が無い場合だけ、
最後の1スロットを切詰め通知に充てます。

## 6. デバッグの勘所

**記録が空。** `stats().windows` を見てください。0なら `runBegin` を
忘れています。バスやピンの操作は `runBegin` の前だと環境から
**見えてすらいません**（フックを入れるのが `runBegin` のため）。

**応答がtick境界へ丸められる。** `HostPort` で `requestWake` を
実装し忘れています（基底は何もせず `false` を返します）。
これは実際に一度やりました——症状は「500 us刻みのはずが1,000 us刻みになる」でした。

**`diag.deferred_full` が出る。** 1回の呼び出しで効果を出しすぎています。
§3.3のとおり、模型側を時間軸に沿った形へ直してください。

**`dropped` が0でない。** 記録が欠けています。畳める周期が無いほど
多様なイベントを出しているということなので、要約できる経路
（transaction単位の記録など）が使えないか検討してください。

**トレースの `x8..007000` は何か。** 繰り返しが畳まれた印です。
「この行が8回起き、最後は007000だった」という意味です。
