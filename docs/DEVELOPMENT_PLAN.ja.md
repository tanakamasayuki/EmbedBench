# 開発計画 — 実験から仕様を固める順序

内部の記録。日本語のみ。EmbedBenchの公開仕様を決める前に、何を調べ、どの順序で
承認し、どの成果物が揃ったら次へ進むかを定める。

この文書は**工程の正本**であり、API仕様の正本ではない。設計上の候補はここに書けるが、
承認ゲートを通るまでは仕様として扱わない。

## 1. 目的

最終的に作るものは、Arduinoアプリケーションを無改造のままhost上で実行し、
外部世界とのやり取りを決定的に再現・観測できる検証ライブラリである。

今回の実行モデルは、`setup()` / `loop()`、Arduinoの時間API、バス、GPIO、
それらから同期的に呼ばれるcallbackからなる標準的なArduino環境に限定する。
FreeRTOS task/queue/semaphore/task notificationや`esp_timer`など、ボード固有の
並行実行・タイマ機構は今回の対象外とする。

最低限、次の問いに再現可能な答えを出せるようにする。

1. アプリが、いつ、どのGPIO・バス・UART・時間APIを操作したか
2. 接続したデバイス模型が、何を受け取り、何を返したか
3. テスト側が、いつ、どの外部入力を注入したか
4. 同じ入力で、同じ順序・同じ時刻・同じ最終状態になるか
5. 実行結果の差を、人が行単位で読んで判断できるか

## 2. 進め方の原則

### 2.1 大きな意味を先に、小さな名前を後に決める

次の順で固定する。

1. 対象範囲と、アクターごとの責務
2. すべての操作が通る経路
3. 時間・順序・ログの意味
4. デバイス模型の最小共通境界
5. 容量、失敗、再入などの異常系
6. C++の型と関数一覧
7. 名前、ヘッダ配置、糖衣API
8. 直列化テキストの細部

関数名やファイル名から先に決めない。同じ意味を複数の候補実装で試し、利用コード、
ログ、容量、失敗時の見え方を比較してから公開仕様へ昇格する。

### 2.2 事実・候補・決定を混ぜない

- **事実**: host coreまたは試作を実行して得た数値
- **候補**: 実験用コードで試している方式
- **決定**: 承認ゲートを通り、決定台帳へ記録したもの

実験が通っただけでは決定にならない。現在の結果は
[EXPERIMENTS.ja.md](EXPERIMENTS.ja.md) に事実・候補として置く。

### 2.3 仕様は縦に薄く固定する

GPIO、I2C、SPI、UARTを全部実装してから仕様化するのではなく、最初は1本のI2C経路で
次を端から端まで成立させる。

```text
アプリ → Arduino API → host hook → EmbedBench → ログ → デバイス模型
                                             ← 応答
テスト → 外部入力の注入 ──────────────────────┘
```

この縦切りで共通の意味を固定し、別のバスを追加しても意味が変わらないことを確認する。

## 3. 仕様を固める単位と承認ゲート

### Gate A — 対象範囲と経路

最初に承認する大枠。ここが決まるまで公開APIを作らない。

決めること:

- EmbedBenchが観測する実行区間
- アプリ、host中間層、EmbedBench核、デバイス、進行役、listenerの責務
- 「ログに漏れがない」の定義
- 走行中に許可する直接呼び出しと禁止する直接呼び出し
- host coreの単一hookを誰が所有するか

必要な成果物:

- アクター図
- 操作経路表
- ログ完全性表
- 直接呼び出し規則
- 最小I2Cシーケンスの手書き例

完了条件:

- 外部から見える状態変更のすべてについて、誰が呼び、どこでログになり、誰が応答するか
  を1行ずつ説明できる
- 「この操作はログに残らない」が暗黙に存在しない

### Gate B — 時間・順序・イベントの意味

Gate Aの経路を、決定的な1本のイベント列へ載せる。

決めること:

- 主時計の単位と範囲
- timestampを付ける場所
- 同一timestamp内の全順序
- tick境界とwait、loop、`yield()` の関係
- 文脈と出どころの分類
- 1イベントの意味的なフィールド

この段階では、JSONLか独自テキストかなどの最終的な綴りは決めない。

必要な成果物:

- イベント意味モデル
- 時間進行図
- 同一時刻に複数イベントが起きるテスト
- waitが複数tickをまたぐテスト
- timestamp wrapとsequence上限の試算

完了条件:

- 同じ入力を複数回実行して、意味上同じイベント列になる
- timestampが同じイベントも一意に並べられる
- イベントを記録する場所が各経路で1か所に定まる

### Gate C — デバイス模型の境界

デバイス固有の書きやすさを残しながら、走行中の操作を共通経路へ載せる。

決めること:

- attachと束縛の責務
- バスごとのops
- 世界からデバイスへ入る物理量・通知などのchannel
- デバイスから世界へ出るGPIO・UARTなどのtool/sink
- 仕込み、検分、dumpの扱い
- デバイス内部イベントを記録する必要範囲

必要な成果物:

- register-map型デバイス1個
- command型デバイス1個
- それぞれの直接API版と共通経路版の呼び出しコード比較
- 1操作あたりの記述量と必要な状態サイズ

完了条件:

- 共通IFのために単純な模型が不自然に長くならない
- 走行中の外部状態変更がEmbedBenchを迂回しない
- 模型がhost coreやArduino型を知らずに実装できる

### Gate D — 容量・失敗・再入

正常系の形が決まった後、有限資源と壊れ方を固定する。

決めること:

- listener、device、channel、保留イベントの上限
- ログバッファ満杯時の動作
- 未接続宛先、重複attach、NACK、overflowの表現
- listenerまたはdevice callbackからの再入
- tick/ISR/進行役で禁止する操作
- エラーを戻り値、診断イベント、停止のどれで伝えるか

必要な成果物:

- 各上限を超えるテスト
- callback再入テスト
- ログ欠落を黙って成功にしないテスト
- 失敗後も状態とログが矛盾しないテスト

### Gate E — 公開APIとファイル構成

Gate A〜Dで意味と制約が固まってから、初めて名前とC++ APIを固定する。

決めること:

- ライブラリ名と接頭辞
- 公開ヘッダと内部ヘッダ
- ctx、event、ops、handleの型
- C++11での初期化方法
- Arduino用糖衣と、核との依存方向
- バージョン互換規則

必要な成果物:

- 最小利用例
- すべての公開ヘッダを単独includeするビルドテスト
- 未使用機能が不要な依存を引かない確認
- API一覧と変更規則

### Gate F — ログ直列化とgolden運用

イベントの意味が固定された後、人が読む1行形式を確定する。

決めること:

- フィールド順
- 数値の基数と桁
- 文字列、バイト列、改行、非ASCIIのescape
- 未知フィールド・未知イベントの読み飛ばし
- goldenで除外可能なフィールド
- 大量転送を1byteずつ書くか、塊として書くか

必要な成果物:

- 同じイベントを複数形式で出した比較
- 1,000 / 100,000イベント時のファイルサイズと生成時間
- `diff`、`rg`、簡単なparserでの扱いやすさ比較
- 形式のversionを増やさず拡張できるテスト

## 4. ログ完全性の考え方

### 4.1 「全部」の範囲を定義する

メモリへのあらゆる代入を記録することは目的ではない。漏れなく残す対象は、
**実行区間中に外部から観測可能な因果を生む操作**とする候補が最も扱いやすい。

対象候補:

- アプリが行ったGPIO・Analog・PWM・SPI・I2C・UART・時間操作
- 進行役が行った線・物理量・通知・UART受信の注入
- デバイスが返したバス応答、GPIO出力、UART送信
- attach/detach、dump、overflow、未接続、禁止操作などの診断

単なるconst検分や、模型内部の計算途中まで全て記録すると、ログが実装詳細へ依存して
模型を変更できなくなる。どの内部状態変化を公開イベントにするかはGate Cで決める。

### 4.2 直接呼び出しを3種類に分ける

共通IFを巨大にせずログの穴も作らないため、直接呼び出しを一律禁止・一律許可にはしない。

| 呼び出し | 候補規則 | ログ |
| --- | --- | --- |
| 走行前の仕込み | デバイス固有の型付きAPIを直接呼べる | 各操作は記録しない。attach後の初期dumpで開始状態を残す |
| 走行中の状態変更 | 直接のmutating APIは禁止。EmbedBenchの注入/channel経由 | 必ず記録する |
| 走行中・走行後のconst検分 | デバイス固有の型付きAPIを直接呼べる | 通常は記録しない。証拠に残す場合だけEmbedBench経由dump |

これなら、温度センサー固有の詳細な設定関数まで共通化する必要はない。一方、走行中に
「温度を80へ変える」「GPSに次の文を出させる」といった外部世界の操作だけは、少数の
共通channel経路に載せられる。

### 4.3 デバイスからの「ログだけ通知」を主経路にしない

次の2案を比較対象にする。

#### 案A — EmbedBench経路で操作し、その場で記録してから配送

```text
caller → EmbedBench（sequence/timestamp付与・記録）→ device
```

利点:

- 操作とログを同じ場所で扱える
- ログだけ失敗、操作だけ成功という分離が起きにくい
- 出どころと順序を中央で確定できる

欠点:

- 全操作を共通化するとIFが巨大で呼び出しが不自然になる

対策候補は、共通化するのを**走行中の外部作用だけ**に限定し、仕込みとconst検分は
デバイス固有APIのまま残すこと。

#### 案B — デバイスを直接操作し、デバイスがEmbedBenchへログだけ通知

```text
caller → device → EmbedBenchへ通知
```

利点:

- デバイス固有APIを自然に書ける

欠点:

- 通知忘れを検出できない
- 操作とログの成功・失敗が分かれる
- sequence/timestampを付ける瞬間が操作より後になる
- 直接呼び出し元の出どころをデバイスだけでは判断できない

現時点では案Aを軸に実験する。ただし巨大な共通IFは作らず、Gate Cで呼び出しコード量を
比較するまでは決定しない。案Bは補助的な「デバイス内部の診断通知」には使えるが、
外部作用を漏れなく記録する主経路にはしない。

## 5. sequenceとtimestamp

### 5.1 付与する場所

sequenceとtimestampは、デバイスやArduino adapterではなく、EmbedBenchの中央の
イベント受付点で同時に付ける候補とする。

理由:

- 同じ時刻に複数イベントが起きてもsequenceで全順序を持てる
- 各デバイスの時計ずれが生じない
- adapter、注入、デバイス応答を同じ基準で並べられる

timestampは「操作開始」「応答完了」のどちらかをイベント種別ごとに曖昧に選ばない。
Gate Bで、受付時刻を基本として、必要な操作だけ開始と完了を別イベントにするか検証する。

### 5.2 1行の先頭候補

意味モデルが固まる前なので、まだ形式は確定しない。比較する最小候補は次の3つ。

```text
# 候補1: sequenceを先頭にして、同一timestampでも順序が明確
00000042 0000000000123456 main app gpio.write line=5 level=1

# 候補2: timestampを先頭にして、時間軸を人が追いやすい
0000000000123456 00000042 main app gpio.write line=5 level=1

# 候補3: JSON Lines。機械処理は容易だが、人のdiffと容量を比較する
{"seq":42,"time_us":123456,"ctx":"main","origin":"app","event":"gpio.write","line":5,"level":1}
```

比較項目:

- 行diffで最初に目へ入る情報
- timestampが同じイベントの読みやすさ
- 固定幅によるファイルサイズ
- byte列と文字列のescape
- 未知フィールドの追加
- 100,000行の生成・parse時間

暫定的には`sequence → timestamp → context → origin → event → payload`を基準候補にする。
timestampだけでは同値が発生するため、ログの識別子にはしない。

### 5.3 timestampの時計

比較する候補:

- 仮想の単調µs時計だけを記録する
- 仮想時刻に加えてtick番号を記録する
- 実時間も補助フィールドとして持つ

通常のgoldenへ実時間を入れると再現性が失われるため、実時間は性能計測用の別記録に
分ける方向で検証する。tick番号はtimestampとsequenceから導けるなら冗長なので、
必要な利用例が出るまで追加しない。

## 6. 作業パッケージ

複数の担当者が衝突せず進められる単位に分ける。各作業は、入力、成果物、完了条件を持つ。

### WP-A1 操作経路表

- 入力: TinyGFXの既存テスト、host core 1.7.0のhook一覧
- 成果物: `docs/EVENT_MATRIX.ja.md`
- 内容: GPIO / Analog / PWM / SPI / I2C / UART / time / lifecycleについて、操作、観測、応答、注入、失敗を列挙
- 完了条件: 全行に記録点と応答担当がある

### WP-A2 直接呼び出し比較

- 入力: Gate Aの候補規則
- 成果物: `tests/device_route_*` と数値表
- 内容: 全直接、全共通IF、仕込み/実行/検分分離の3案を同じ模型で比較
- 測る値: 利用側行数、device側行数、callback数、ログ欠落数、型変換数

### WP-B1 時計境界

- 入力: 現在の`clock/`、`tick_split/`
- 成果物: 境界値テスト
- 内容: 0、1、999、1000、1001us、複数tick、wrap直前、wait内の再入
- 完了条件: 期待するtick回数と順序を全ケースで数値化

### WP-B2 イベント形式比較

- 入力: Gate Bの意味フィールド
- 成果物: 3形式のwriter/parser試作と比較表
- 測る値: bytes/event、100,000件の生成時間・parse時間、差分行数
- 注意: この段階のwriterは公開APIへ入れない

### WP-C1 I2C縦切り

- 入力: Gate A/Bの決定
- 成果物: 1つのregister-map模型、attach、write/read、注入、dump、golden
- 完了条件: アプリ無改造、イベント欠落0、同一結果を3回再現

### WP-C2 command型縦切り

- 入力: WP-C1の共通境界
- 成果物: 表示またはUART系の状態機械模型
- 完了条件: register-map型の都合をcommand型へ押し付けず同じ核を使える

### WP-D1 多重化と上限

- 入力: `hook_slots/` の結果
- 成果物: listener 0/1/N、上限、解除、callback中解除の実験
- 測る値: 1イベントあたりcallback数、状態サイズ、上限時の戻り値と診断件数

### WP-D2 ログ満杯

- 入力: イベント意味モデル
- 成果物: 固定バッファ満杯の比較
- 比較: 新規を捨てる、古いものを上書き、即時停止、外部sinkへ逐次送る
- 完了条件: 欠落が必ず検出可能で、操作だけ成功してログ欠落を隠さない

## 7. 並行作業のルール

- Gate未承認の型や名前を`src/`へ追加しない。試作は`tests/<experiment>/`内に閉じる
- 各実験は別ディレクトリにし、別実験の生成物を読まない
- 数値結果は[EXPERIMENTS.ja.md](EXPERIMENTS.ja.md)へ追記する
- 判断が必要になったら、候補、測定値、利点、欠点を揃えてから承認を求める
- 既存の実験結果を変更する場合は、理由とhost coreのversionを記録する
- コードコメントは英語、未確定の説明文書は日本語のみとする
- 1つの担当作業で、実験、公開API追加、命名確定を同時に行わない

## 8. 当面やらないこと

- 実機テストと実機用設定
- FreeRTOS task/queue/semaphore/task notificationと`esp_timer`の仮想化
- ESP32など別環境への移植
- 公開API名の確定
- 標準デバイスカタログの大量追加
- GUIや波形ビューア
- サイクル精度・電気特性の再現
- ログ形式を先に固定してからイベントを合わせること
- すべてのデバイス固有操作を1つの巨大な共通IFへ押し込むこと

## 9. 現在地

現在の`src/EmbedBench.h`はversion以外の公開APIを持たない。既存の`smoke/`、
`clock/`、`lifecycle/`、`ports/`、`tick_split/`、`hook_slots/`はhost core 1.7.0の
性質を確認する準備計測であり、Gate A以降の仕様決定ではない。

次に行うのはGate AのためのWP-A1とWP-A2。操作経路と直接呼び出しの境界を承認してから、
timestampや1行形式をGate Bで比較する。
