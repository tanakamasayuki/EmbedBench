## 0. 結論（先に）

1. **§9.4の分担の読みは正しい。** `reset` / `channelRead` / `dump` を副作用禁止と
   契約したのは、まさに検分を critical path の外へ出すためで、
   preloadとreadbackがそこに乗るのは設計どおりである。
2. **ただし「模型がそのまま実機の線に載る」は成り立たない。**
   模型23種のうち**6つは時間定数を意図的に圧縮している**。
   特にModbusは実物 4,010 µs に対し模型 1,500 µs で、9600 baudの1文字（1,146 µs）より
   短い。**DUTの送信途中でフレーム完結と判断しうる**——タイミング精度の話ではなく
   機能が壊れる。peerとして使う模型は定数の扱いを決めないと危ない（E-1）。
3. **`requestWake` を実装しない環境は、静かに劣化する。**
   基底実装は何もせず `false` を返すだけで、模型は「wakeが来ない」と気づけない。
   この取りこぼしは**本プロジェクトで実際に起きた**（症状は
   「500 µs刻みのはずが1,000 µs刻みになる」で、原因に辿り着くのに時間がかかった）。
   宣言と失敗を明示してほしい（E-2）。
4. **再入禁止は模型の前提であって、努力目標ではない。**
   23種すべてが「自分の実行中に自分へ再入されない」ことを前提に書かれている。
   実機の割り込みで破られると状態が壊れる（E-3）。
5. **「器」は2つ、EmbedBench側に既にある。** §9.3の register file と block device は
   `regmap_model` と `unit_sdcard_model` がそのままで、後者は生ブロックの流し込みと
   本物のFAT12プリセット7枚を持つ。firmware側の実装を減らせる（§4）。
6. **模型の版はEmbedBenchが採番する**（§11-10への回答）。ただし版が意味するのは
   ソースではなく**観測可能な振る舞い**にしたい（E-6）。

## 2. 依頼事項

### E-1. 圧縮された時間定数の扱いを決める（最優先）

- **要求**: 模型をバスのpeerとして使う場合、
  (a) 圧縮された定数を実物の値へ設定できる経路を用意するか、
  (b) 圧縮された模型をpeerに使わないと決めるか、
  どちらかを選んでほしい。**こちらは (a) の実装を引き受けられる。**
- **根拠**: 模型の時間定数は仮想時計上での読みやすさで選ばれている。
  各定数には物理値との関係が書いてあり、書かれていなければテストが落ちる。
  現在圧縮しているのは6つ。

  | 模型 | 定数 | 実物 | 模型 |
  | --- | --- | ---: | ---: |
  | `unit_modbus_model` | `kFrameGapUs` | 約4,010 µs @9600 | 1,500 µs |
  | `unit_ir_model` | `kRepeatPeriodUs` | 約108 ms | 2,000 µs |
  | `gps_model` | `kDefaultPeriodUs` | 1 s | 2,000 µs |
  | `unit_pir_model` | `kHoldUs` | 数秒〜数分 | 2,500 µs |
  | `unit_flash_model` | `kEraseUs` | 数秒〜数十秒 | 8,000 µs |
  | `unit_lora_model` | `kAirTimePerByteUs` | 設定次第でms級 | 1,000 µs |

  残りは物理値なので、そのままpeerにしてよい。
- **なぜ危ないか**: Modbusが最悪で、模型の1,500 µsは9600 baudの1文字（1,146 µs）より
  わずかに長いだけである。DUTがバイト間に少しでも間を空ければ、
  **模型は送信途中のフレームを完結と判断する**。§9.3の表が扱っているのは
  「遅すぎて成立しない」だが、こちらは**速すぎて誤動作する**方向で、見落としやすい。

### E-2. `requestWake` の実装を宣言し、無ければ失敗させる

- **要求**: `caps` に「模型の時刻要求に応えられるか」と**その分解能**を載せる。
  応えられない環境で、それを要る模型を束縛したら **fail closed** にしてほしい。
- **根拠**: `HostPort::requestWake` の基底実装は何もせず `false` を返す。
  模型は戻り値を見て「境界だけで動く」へ退避できる契約だが、
  **退避したことはログに出ない**。結果は「なんとなく遅い」で、原因が分かりにくい。
  本プロジェクトで実際に踏んだ（`units_race` 実装時、adapterでの override 忘れ）。
- **どの模型が要るか**: `requestWake` を呼ぶ模型は12種。
  自走するもの（IMU・GPS・IR・PIR）と、応答に遅延を持つもの（環境センサー・
  SDカード・SPI flash・Modbus・UWB・超音波）。

### E-3. 再入禁止を契約として明示する

- **要求**: 「デバイスの実行中に、そのデバイスへ再入しない」を probe 環境の
  実装契約として明示してほしい。実機の割り込みで生じた効果は、
  デバイスから戻ってから配送する。
- **根拠**: 模型23種すべてがこれを前提に書かれている。
  `frameOut()` を呼んでも、その中で自分の `frameIn()` が呼ばれないので、
  状態を一貫させたまま効果を出せる。破られると状態機械が壊れる。
- **付随して**: 保留にも容量が要り、**溢れたら必ず診断を出してほしい**（無音で捨てない）。
  この点は本プロジェクトでも一度踏んでおり、そのときは
  **環境ではなく模型が誤っていた**（1回の呼び出しで10フレーム出していた）。
  診断が出たからこそ気づけた。

### E-4. 診断の語彙とイベント行の形を揃える（§7段2をやる場合）

- **要求**: `harness-probe.ja.md` §6-3 の diff をやるなら、
  診断名（`diag.unbound` / `diag.chan_reject` / `diag.deferred_full` ほか）と
  イベント行の形をこちらに合わせてほしい。合わせないなら、
  **diffは「機能的な署名」だけに限る**と最初に決めてほしい。
- **根拠**: 準拠キットはここを検査していない。
  **語彙が違っても両方とも準拠**だが、行単位の比較だけが成立しなくなる。
  覆っている範囲・いない範囲は [FACTS.ja.md](FACTS.ja.md) に書いた。
- **重要（§6-3の前提の訂正）**: イベント行は時刻を含むので、
  **素の行単位diffは全行が差分になる**。
  そちらの `test-strategy` が既に持っている
  **functional signature と timing result の2層判定をdiffにも適用**するのが答えで、
  `(origin, text)` の列は完全一致、時刻は許容差で比較、という形になる。
  ここを決めずに始めると、最初の実行で提案全体が死んだように見える。

### E-5. `caps` に凍結IFの版を載せる

- **要求**: `caps` に `embedbench_if: { version, revision }` を含めてほしい。
- **根拠**: 模型は凍結IFに対して書かれており、IFはrevisionで前進する
  （現在 v1 / rev 004）。probeに載っている模型がどのrevisionのIFで
  ビルドされたかは、模型の版とは別に効く。

### E-6. 模型の版はEmbedBenchが採番する（§11-10への回答）

- **回答**: こちらが持つ。模型のコードはこちらのものなので自然である。
- **提案する規則**: 版が数えるのは**観測可能な振る舞い**であって、ソースではない。
  - コメント・整形・内部実装の変更 → **据え置き**
  - 応答内容・時間定数・診断文言・channel割り当ての変更 → **繰り上げ**
  - 版は模型ごとに独立（`model:sdcard@2` はSDカード模型だけの版）
- **こちらでやること**: 各模型に版の定数を置き、テストで固定する
  （据え置き／繰り上げが意図的な操作になる）。着手はそちらの採否が決まってからでよい。

### E-7. どの模型を既定プロファイルに入れるか（§11-8への回答）

- **回答**: 全部載せる必要はない。判断材料として:
  - **peerとして安全**（物理値）: `regmap_model`・`env_sensor_model`・`temp_model`・
    `unit_encoder_model`・`unit_sdcard_model`・`unit_flash_model`・`unit_codec_model`・
    `unit_imu_model`・`unit_rtc_model`・`unit_faulty_model`
  - **E-1の扱いを決めてから**: `unit_modbus_model`・`gps_model`・`unit_ir_model`・
    `unit_pir_model`・`unit_lora_model`
  - **frame経路なので実線には載らない**: `unit_ir_model`・`unit_lora_model`・
    `unit_uwb_model`・`unit_chunk_model`・`node_model`
    （論理ビット＋format情報の対であって、波形ではない。§9の「器」とも別物）
- **`unit_faulty_model` を推す**。障害注入（無応答・data NACK・途中で切れる読み出し・
  間欠故障）を決定的に起こせる唯一の模型で、実物では狙って再現できない。

## 4. EmbedBench側から出せるもの

そちらの実装を減らせるもの。**要望ではなく提供**。

| §9.3の分類 | EmbedBench側にあるもの |
| --- | --- |
| 器: register file | `regmap_model`。register mapとrepeated startの扱いを持つ |
| 器: block device | `unit_sdcard_model`。512バイト×8、`loadBlocks()` で生イメージを流し込める |
| 器: byte stream | 相当するものは無い。`unit_modbus_model` / `gps_model` は模型側 |

**SDカードのプリセット7枚**は、生成器が本物のFAT12として構築し、
**ドライバと同じ手順で解析し直してから**Cソースを出している。
正常・空・boot signature破損に加え、**巡回するクラスタ鎖・範囲外クラスタ・
サイズと鎖の不一致・bytes-per-sectorがゼロ**を含む。
巡回鎖はガードの無いドライバをハングさせるので、コア側のFATドライバ試験に
そのまま使えるはずである。

## 5. 環境実装をどちらに置くか

**probe側を推す。** 根拠:

- EmbedBenchの環境は「プラットホーム別の実装例」であり、契約は凍結IFである。
  模型は `devices/` として**独立したArduinoライブラリ**にしてあり、
  他所から消費されることを想定している。
  harnessが `embedbench_device.h` + `devices/` に依存するのが**想定した消費形**。
- EmbedBench側に置くと、現在g++とarduino-cli hostだけで回っているリポジトリに
  RP2040のツールチェーンが入る。CIも覆えない。
- **方針との整合**: 計画の「当面やらないこと」にある「別環境への移植」は
  EmbedBench自身の移植をしない宣言であって、他所が凍結IFに対して環境を書くことは
  **IFが設計どおり働いている状態**である。むしろ
  [SCOPE](DEVICE_IF_SCOPE.ja.md) 3.3節が「越える要望は実機テストへ振り分ける」と
  書いており、その受け皿が実在すること自体がこちらの利益になる。
  逆にEmbedBench側へ置く場合は計画の改訂が要る。

**受け入れ試験は既にある。** `tests/conformance/` が1つのprobeと1つのシナリオで
環境を検査し、既存2実装が同じ判定に達することを確認している。第3の環境は
これを通すべきで、新たに考案する必要はない。必須8項目・観測のみ4項目・
**覆っていない3項目**は [FACTS.ja.md](FACTS.ja.md) に書いた。

## 6. 注意（§0-5への補足）

`harness-probe.ja.md` §0-5 の「差分に残るものがそのままコアのバグ候補」は、
そのままでは強すぎる。差分には少なくとも次が乗る。

- E-1の時間定数（模型の便宜値）
- E-4の時刻（仮想時計と実時間）
- 記録の畳み込み。満杯時に繰り返し周期を1周＋回数へ畳むので、
  **容量の違う2環境は畳む位置が違い、行数が合わない**
  （実測: 27,375イベントが61行に畳まれた例がある）
- 効果の遅延配送が実時間を持つこと（そちらの§6-4-2の指摘どおり）
- こちらの既知の制限（`delayMicroseconds(1000)` はwakeを跨ぐと最大1 wake早く戻る）

**最小の模型1つでノイズをゼロにしてから模型を増やす**、という段取りを推す。
比較実行用に畳み込みを止めた出力は、こちらで用意できる。

## 7. こちらで先にやっておけること

そちらの採否が決まる前でも進められるもの。**指示があれば着手する。**

1. 圧縮された時間定数を、構築時またはpreloadで設定できるようにする（E-1の(a)）
2. 模型に版の定数を置き、テストで固定する（E-6）
3. 比較実行用の出力（畳み込み無効、時刻を別列）を用意する（§6）
4. 準拠キットが第3の環境の門として足りるかを見直し、
   足りなければ「覆っていない3項目」を検査に足す
